# JDK Flight Recorder Workflow

JFR is the primary automated JVM evidence layer for this laboratory. It does not remove every profiler effect, and the repository never describes it as literally zero overhead. The selected event profile, thresholds, stack traces, and sampling periods define the cost and the evidence that can be observed.

The common startup form below is valid for a standalone application:

```bash
java -XX:StartFlightRecording=duration=60m,filename=recording.jfr,settings=default \
  -jar application.jar
```

It is **not** the canonical lab protocol. A startup recording mixes initialization, warm-up, idle time, and measured load. This lab starts and stops JFR with `jcmd` around the exact k6 measured window so MVC and WebFlux receive the same bounded profiling interval. The short custom profile is deliberately richer than the low-overhead `default.jfc` continuous-recording profile.

Raw `.jfr` files can be reopened offline in JDK Mission Control or a current standalone VisualVM release. Numeric documentation is generated by the JFR consumer API and the `jfr` command-line views, not copied from GUI charts.

## Automated container path

The evidence Compose override builds the selected checkout service with a Java 21 JDK runtime so `jcmd` and `jfr` are available inside the container. Normal application execution continues to use the smaller JRE image.

Run one complete recording:

```bash
labs/01-loom-vs-reactive-checkout/scripts/run-evidence.sh \
  --implementation mvc-vthreads \
  --scenario moderate
```

The script automatically:

```text
copies docs/profiling/evidence-profile.jfc into the container
starts JFR through jcmd as the same UID as the Java process
runs warm-up and measured load
stops and copies the recording
creates jfr summary and predefined views
captures bounded virtual-thread failure details plus aggregate concurrency-event counts
```

## Evidence profile

`evidence-profile.jfc` is based on JDK 21 `profile.jfc` and configures:

- high method profiling;
- medium allocation profiling;
- thread dumps every 10 seconds;
- 10 ms locking and socket thresholds;
- `jdk.VirtualThreadPinned` with stack traces and a 10 ms threshold.

The profile is intentionally symmetric: both MVC and WebFlux runs use the same event settings.

## Automatically generated reports

```text
jfr-reports/summary.txt
jfr-reports/hot-methods.txt
jfr-reports/allocation-by-class.txt
jfr-reports/allocation-by-site.txt
jfr-reports/gc.txt
jfr-reports/gc-pauses.txt
jfr-reports/thread-count.txt
jfr-reports/thread-cpu-load.txt
jfr-reports/pinned-threads.txt
jfr-reports/socket-reads-by-host.txt
jfr-reports/concurrency-event-counts.txt
jfr-reports/virtual-thread-events.json.gz
```

The pipeline deliberately does not export every `ThreadPark` and `JavaMonitorEnter` event as JSON: verbose stack expansion can turn a small binary recording into hundreds of megabytes. Counts, predefined views, and the original `.jfr` remain the evidence source. The `jfr` CLI can print, summarize, configure, scrub, and aggregate recording data. JDK Mission Control and VisualVM may be used for interactive review of the same `recording.jfr` file.

## Automated extraction and documentation

Each run creates:

```text
jfr-reports/jfr-metrics.json
jfr-reports/JFR_METRICS.md
```

After a suite finishes, materialize all comparative documentation without copy and paste:

```bash
labs/01-loom-vs-reactive-checkout/scripts/materialize-evidence-docs.sh \
  .artifacts/evidence/<SUITE_ID> \
  --update-analysis
```

See [`AUTOMATED_DOCUMENTATION_WORKFLOW.md`](AUTOMATED_DOCUMENTATION_WORKFLOW.md).

## Interpretation guardrails

- A hot method is a sampled observation, not automatically an optimization target.
- No pinned-thread events does not prove that pinning is impossible.
- Allocation rate is not retained heap.
- JFR-enabled evidence describes the profiler-enabled protocol.
- Always connect an interpretation to the run ID, Git SHA, scenario, and other supporting artifacts.

## Publishing

Raw `.jfr` files belong under `.artifacts/` or a GitHub Release asset. Commit small text views and written interpretation only after sanitization.
